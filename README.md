# ЭВОЛЮЦИЯ — Публикатор статей

Внутренний инструмент для автоматизации публикации статей на сайт
спецодежды и средств индивидуальной защиты evosiz.ru: редакция кладёт
`.docx` статьи в папку на общем Google Диске → выбираешь файл в
интерфейсе → он автоматически разбирается на нужные поля, включая
SEO-title/description/ключевые слова из служебного блока в документе и
картинки, вставленные прямо в текст → генерируешь превью-картинку в
фирменном стиле → публикуешь одной кнопкой в Strapi (черновиком или сразу).

Это переработанная версия внутреннего инструмента article-demo под другой
сайт — см. раздел
[Чем этот инструмент отличается от article-demo](#чем-этот-инструмент-отличается-от-article-demo).

## Что делает инструмент

1. **Список статей** — показывает содержимое папки на Google Диске
   (`GOOGLE_DRIVE_ROOT_FOLDER_ID` в `.env`): вложенные папки можно
   использовать как категории или как угодно ещё — интерфейс просто
   позволяет кликами заходить внутрь (хлебные крошки сверху), пока не
   дойдёшь до нужного `.docx` файла или Google Docs документа.
2. **Парсинг** — по клику на файл скачивает его (обычный `.docx` — напрямую,
   Google Docs документ — через экспорт в `.docx`) и вытаскивает: заголовок,
   SEO-title, meta description, ключевые слова (из служебного блока в
   начале документа — редакция пишет его сама, см.
   [Формат исходных .docx](#формат-исходных-docx)) и тело статьи — от
   заголовка и до конца раздела FAQ включительно, если он есть (всё, что
   идёт после — служебные пометки, ключевые слова, теги — в публикацию не
   попадает). Картинки, вставленные прямо в документ, достаются и
   расставляются по своим местам автоматически.
3. **Редактирование** — все поля можно поправить прямо в интерфейсе перед
   публикацией: название (оно же SEO-title — это одно поле), slug,
   markdown статьи (с живым предпросмотром), meta description, ключевые
   слова. Кнопка ↻ рядом со slug генерирует его заново из названия и
   проверяет в Strapi, что такого ещё нет (при совпадении добавляет
   `-2`, `-3` и т.д.).
4. **Превью-картинка** — генерируется нейросетью (`gpt-image-2`) в
   фирменном стиле Эволюции: диагональная синяя панель с заголовком слева,
   фото по теме статьи справа, 1920×1080. Логотип "ЭВОЛЮЦИЯ" **не
   рисуется нейросетью**, а накладывается кодом поверх — гарантированно
   одинаковый каждый раз. Это единственное место, где инструмент
   обращается к нейросети — SEO-поля она не генерирует.
5. **Публикация** — статья создаётся в Strapi с правильной структурой
   полей (`title`, `slug`, `body`, вложенный `metadata`), картинки из
   статьи и обложка сами заливаются в Media Library. По умолчанию — черновик.
   Файлы в Media Library называются по slug статьи: `<slug>-cover.png` для
   обложки и `<slug>-1.jpeg`, `<slug>-2.png` ... для картинок из текста, в
   порядке появления — так их легко найти поиском в «API Uploads».
   Можно выбрать категорию, опубликовать сразу или **отложить публикацию**
   на дату и время: черновик создаётся сразу, а время срабатывания хранит
   сам Strapi (плагин Publisher), так что backend после этого не нужен.
   И для «опубликовать сразу», и для отложенной публикации нужна
   сгенерированная превью-картинка — в Strapi это поле обязательное.
   К статье можно прикрепить **видео**: галочка «В статье есть видео»,
   ссылка на YouTube, Rutube или Vimeo (бэкенд сам вычленяет из неё тип и
   id, `video_utils.py`) и название видео. Видео кладётся в одиночный
   компонент Strapi — поле `video` или `bottomVideo` (выбирается в
   интерфейсе); обе структуры одинаковые: `title`, `type`, `value`.

## Архитектура

```
┌─────────────────┐        ┌──────────────────┐        ┌─────────┐
│  Next.js frontend │ <---> │  FastAPI backend  │ <---> │  Strapi │
│   (localhost:3000) │      │  (localhost:8001)  │      │  (CMS)   │
└─────────────────┘        └────────┬─────────┘        └─────────┘
                                     │
                       ┌─────────────┴─────────────┐
                       ▼                            ▼
                Google Drive API              OpenAI / ProxyAPI
          (папки и файлы со статьями,        (только превью-картинки)
           экспорт Google Docs в .docx)
```

Backend и frontend — два отдельных процесса, оба должны быть запущены
одновременно. Backend ни от чего не зависит, кроме .env; frontend просто
ходит на backend по HTTP.

## Установка и запуск локально

Нужно два открытых терминала одновременно.

**Терминал 1 — backend:**
```bash
python -m venv venv
venv\Scripts\activate          # Windows; на Mac/Linux: source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env           # и заполнить своими значениями (см. таблицу ниже)
uvicorn main:app --reload --port 8001
```
Также нужен установленный в системе **pandoc** (не Python-пакет, а
отдельная программа): `brew install pandoc` / `apt install pandoc` /
[pandoc.org](https://pandoc.org/installing.html) для Windows.

**Терминал 2 — frontend:**
```bash
cd frontend
npm install
npm run dev
```

Открыть **http://localhost:3000**. В правом верхнем углу должно быть
написано "сервер подключён" — если "сервер недоступен", см. раздел
[Частые проблемы](#частые-проблемы-и-их-причины).

## Переменные окружения (.env)

| Переменная | Обязательна | Назначение |
|---|---|---|
| `GOOGLE_API_KEY` | да | Ключ для Google Drive API (список папок/файлов, экспорт Google Docs в .docx) — console.cloud.google.com, включить Google Drive API |
| `GOOGLE_DRIVE_ROOT_FOLDER_ID` | да | id корневой папки со статьями — кусок ссылки после `/folders/` |
| `STRAPI_URL` | да | Базовый адрес Strapi, без `/api` и без `/admin` на конце |
| `STRAPI_TOKEN` | да | API-токен Strapi (Settings → API Tokens), права: create/find на коллекцию статей, upload на Media Library |
| `STRAPI_DEFAULT_COLLECTION` | нет (по умолчанию `blogs`) | Имя REST-коллекции статей |
| `STRAPI_CATEGORY_COLLECTION` | нет (по умолчанию `blog-categories`) | Имя REST-коллекции категорий для выпадающего списка |
| `STRAPI_ENTITY_SLUG` | нет (по умолчанию `api::blog.blog`) | Идентификатор типа контента для плагина Publisher (отложенная публикация). У API-токена должны быть права Publisher → create |
| `OPENAI_API_KEY` | для генерации превью | Ключ OpenAI или прокси-сервиса (ProxyAPI и т.п.) — используется только для картинок, SEO-поля нейросетью не генерируются |
| `OPENAI_BASE_URL` | только для прокси | Например `https://api.proxyapi.ru/v1`. Пусто = обычный OpenAI напрямую |
| `OPENAI_IMAGE_MODEL` | нет (по умолчанию `gpt-image-2`) | Модель для картинок |
| `OPENAI_TIMEOUT_SECONDS` | нет (по умолчанию 180) | Генерация картинки медленная, таймаут с запасом |
| `APP_PASSWORD` | нет (по умолчанию защита выключена) | Общий пароль доступа — заполняется перед выкладкой в интернет |
| `CORS_ORIGINS` | нет (по умолчанию `localhost:3000`) | Адрес(а) фронтенда через запятую — нужно при деплое |

**Важно:** копируй `.env.example` именно в файл с именем `.env`. После
любого изменения `.env` backend нужно перезапустить — `--reload`
подхватывает изменения в коде, но не в переменных окружения.

## Google Диск: как разложить статьи по папкам

Никакой специальной структуры не требуется — инструмент просто показывает
содержимое папки, как обычный файловый менеджер: вложенные папки можно
кликом открывать (хлебные крошки сверху позволяют вернуться назад), а по
клику на `.docx` файл или Google Docs документ запускается парсинг.
Категории, подкатегории или вообще плоский список — как удобнее редакции.

Корневая папка (и любая вложенная, до которой дойдёт редакция) должна
быть открыта **"Всем, у кого есть ссылка"** — иначе API-ключ не сможет её
прочитать (см. [Частые проблемы](#частые-проблемы-и-их-причины)).
`GOOGLE_DRIVE_ROOT_FOLDER_ID` в `.env` — id именно корневой папки, кусок
ссылки после `/folders/`, например для
`https://drive.google.com/drive/folders/1AbCdEfGhIjKlMnOpQrSt` это
`1AbCdEfGhIjKlMnOpQrSt`.

## Формат исходных .docx

- **Заголовок** — настоящий `# Заголовок` (Word-стиль "Заголовок 1"), если
  он есть в документе; если нет — первый абзац, который не похож на часть
  служебного блока (не строка-маркер `[СЛУЖЕБНОЕ — НЕ ПУБЛИКОВАТЬ]`, не
  одно из известных полей блока и не строка markdown-таблицы). В любом
  случае всё, что стояло в документе ДО найденного заголовка (весь
  служебный блок с метаданными) в тело статьи не попадает — отбрасывается
  целиком, а не только сама строка заголовка.
- **Тело статьи** — от заголовка и до конца раздела FAQ включительно, если
  он есть (заголовок раздела — "Частые вопросы", "Часто задаваемые
  вопросы" или "FAQ"; вопросы — либо `### Вопрос`, либо `**Вопрос**`
  жирным, дальше один абзац-ответ). Всё, что идёт после последнего ответа
  — "Ключевые слова", "Теги", "Похожие статьи" и т.п., которые редакция
  иногда дописывает следом в том же документе — в публикацию не попадает.
  Если раздела FAQ в документе нет — берётся весь текст статьи целиком
  (лучше отдать лишнее, чем случайно обрезать нужный контент).
- **Картинки** — поддерживаются оба варианта:
  1. Вставлены прямо в документ (не ссылками) — извлекаются через
     `pandoc --extract-media` в порядке появления в тексте.
  2. Ссылка на Яндекс.Диск (в любом виде: markdown-ссылка, просто
     URL в тексте, в том числе обёрнутый в `<u>…</u>` от форматирования
     Word) — при парсинге бэкенд скачивает файл по публичной ссылке
     через API Яндекс.Диска (`yandex_disk.py`, как в article-demo). Если
     скачать не получилось (ссылка протухла, доступ закрыт и т.п.) — само
     упоминание ссылки убирается из текста, а не остаётся битой ссылкой;
     в интерфейсе под редактором появляется предупреждение "Не скачалось
     с Яндекс.Диска: N фото", чтобы редакция могла разобраться руками.

  В обоих случаях подписи под картинками вида "Рис. 7 Название"
  очищаются от номера рисунка, но текст подписи (включая ссылки на
  карточки товаров, если они есть) сохраняется.
- **Таблицы** — если у ячеек таблицы сложное форматирование (свой стиль
  абзаца, отступы и т.п.), pandoc вместо markdown-таблицы иногда выдаёт
  сырой HTML (`<table>…</table>`), из-за чего в редакторе видна каша из
  тегов и "пустых строк". Парсер сам разбирает такой HTML и пересобирает
  его в обычную markdown pipe-таблицу.
- **Служебный блок с метаданными** — SEO-title, meta description и
  ключевые слова редакция прописывает сама, обычно перед заголовком
  статьи (так решили — обращаться к нейросети ради этого нецелесообразно).
  Парсер понимает три равноправных формата — тот же код, что в
  article-demo, специально написан так, чтобы не зависеть от того, кто и
  как именно оформил конкретный документ:
  1. `**SEO-title (58 симв.):** значение` / `**Meta description:** значение`
  2. Markdown-таблица `| **title** | значение |` / `| **description** | значение |` / `| **keywords** | значение |`
  3. Ключевые слова отдельно — либо `**ключи:**` со списком на следующей
     строке, либо `**Ключевые слова:** значение` на той же строке
  4. Если `SEO-title` не найден нигде — используется заголовок статьи как fallback

  Если блока нет вообще — поля просто остаются пустыми, заполняются
  вручную в интерфейсе перед публикацией.

Если встретится новый вариант оформления — правки нужно вносить в
`docx_parser.py`, вся эта логика сосредоточена там.

## Как устроена генерация превью

- Единый фирменный стиль (в отличие от article-demo, где было два —
  scene/detail): диагональная сплошная синяя панель (`#0086bc`, тот же
  цвет, что в шапке сайта evosiz.ru) слева, с тонкой более светлой
  голубой линией по срезу, фото по теме статьи справа.
- Заголовок делится на два яруса по первому двоеточию в SEO-title (так
  же, как в article-demo) — например "Руки под защитой: всё о защитных
  перчатках" → крупная строка "Руки под защитой:" и чуть меньшая
  "всё о защитных перчатках" под ней. Без двоеточия — один ярус.
- **Логотип не генерируется нейросетью** — после генерации код
  накладывает настоящий файл `logo.png` (белый леттеринг "ЭВОЛЮЦИЯ" на
  прозрачном фоне) в левый верхний угол через PIL. Файл получен из
  присланного логотипа (синяя плашка с белым текстом) — фон убран, так
  что накладывается только сам белый текст, без синей подложки под ним
  (на превью логотип лежит прямо на синей панели). Тот же прозрачный
  файл используется и в шапке сайта — фон навбара уже синий, поэтому
  подложка с белыми углами вокруг логотипа не нужна и не накладывается.
- **Референс стиля** — можно один раз загрузить эталонное превью через
  интерфейс (`reference_images/preview.png`) — он будет автоматически
  подмешиваться в каждый запрос генерации как образец композиции и
  цветов.
- Итоговый размер всегда ровно 1920×1080 — модель генерирует в ближайшем
  поддерживаемом размере (1536×1024), дальше картинка докадрируется.

## Деплой в продакшн

Backend и frontend деплоятся раздельно — по той же схеме, что и
article-demo:

- **Backend → Render** (или любой хостинг с поддержкой Docker — `Dockerfile`
  нужен из-за `pandoc`). Все переменные из таблицы выше — в Environment
  Variables хостинга, никогда не в коде.
- **Frontend → Vercel** (Root Directory = `frontend`, переменная
  `NEXT_PUBLIC_API_BASE` = адрес задеплоенного backend). Если Vercel
  нестабильно открывается без VPN — можно перенести frontend на Render
  так же, как backend (Node.js Web Service, без Docker).
- После деплоя — вписать реальный адрес фронтенда в `CORS_ORIGINS` на
  backend, иначе браузер будет блокировать запросы.
- Обязательно задать `APP_PASSWORD` перед тем, как открывать доступ кому-то
  кроме себя — форма входа реально проверяет пароль через backend
  (`/api/auth/check`), а не просто закрывается по любому вводу.

## Чем этот инструмент отличается от article-demo

| | article-demo | evolution-publisher |
|---|---|---|
| Источник статей | Google Диск, папки с .docx | То же самое — Google Диск, папки с .docx/Google Docs |
| Картинки статьи | Ссылки на Яндекс.Диск в тексте, скачиваются отдельно | Вставлены прямо в документ, извлекаются из него |
| Заголовок / служебный блок / FAQ | `# H1`, служебный блок перед ним отбрасывается целиком, обрезка тела по концу FAQ | То же самое — H1 либо первый абзац, не похожий на часть служебного блока; обрезка по FAQ восстановлена |
| Категории превью | Две: scene / detail, разные промпты | Одна: диагональная синяя панель |
| Логотип на превью | Правый верхний угол | Левый верхний угол |
| Strapi | Свой сайт, коллекция в `.env` | Тот же клиент (`strapi_client.py` синхронизирован с article-demo: читаемые ошибки, уникальный slug, отложенная публикация), другой сайт/коллекция в `.env` |
| Хранение картинок между шагами | Папка `image_store/` на диске | То же самое |
| Название и SEO-title | Одно поле | То же самое |

## Частые проблемы и их причины

| Симптом | Причина |
|---|---|
| Фронт пишет "сервер недоступен" | backend не запущен, либо поднялся не на том порту |
| Список папок/файлов Google Диска пустой или ошибка 403/404 | папка не открыта "Всем, у кого есть ссылка", либо `GOOGLE_DRIVE_ROOT_FOLDER_ID` в `.env` указывает не туда — backend нужно перезапустить после правки `.env` |
| Не удалось скачать документ (403/404) | конкретный файл внутри папки открыт по-другому, чем сама папка — доступ у Google Docs документов настраивается отдельно |
| Meta description / keywords пустые после парсинга | в документе нет служебного блока с метаданными (или он оформлен как-то по-новому, не так, как в разделе [Формат исходных .docx](#формат-исходных-docx)) — заполни вручную или попроси редакцию добавить блок в документ |
| В тело статьи попал служебный блок целиком (виден "[СЛУЖЕБНОЕ — НЕ ПУБЛИКОВАТЬ]" и SEO-поля в тексте) | в документе нет ни настоящего `# Заголовок`, ни абзаца после блока, который парсер мог бы опознать как заголовок — проверь, что реальное название статьи идёт сразу после последнего поля служебного блока |
| Статья публикуется сразу, а не в черновик | в Strapi 5 без явного параметра `status` запись публикуется автоматически — `strapi_client.py` уже всегда шлёт `status` явно |
| Картинок найдено 0, хотя в документе они есть | документ был передан не как обычный .docx с внедрёнными изображениями (например ссылки на внешние картинки вместо вставленных) |
| Ошибка при отложенной публикации: «черновик создан, но запланировать не удалось» | у API-токена Strapi нет прав Publisher → create, либо плагин Publisher не установлен, либо неверный `STRAPI_ENTITY_SLUG`. Сам черновик при этом уже создан — повторно публиковать не нужно, дату можно поставить в админке Strapi |
| «Нужна превью-картинка» при попытке опубликовать | поле «Превью» в Strapi обязательное при публикации — сначала сгенерируйте превью, либо сохраните как черновик |
| 401 при вызове `/api/publish`, хотя пароль вроде введён | задан `APP_PASSWORD`, но сохранённый в этой вкладке браузера пароль устарел или неверный — окно входа появится снова, введи пароль ещё раз |
| Ошибка про `OPENAI_API_KEY` при генерации превью | ключ не задан или backend не был перезапущен после того, как ключ добавили в `.env` (`--reload` не подхватывает переменные окружения, только код) |
| 403 при генерации через `gpt-image-1`/`gpt-image-2` напрямую от OpenAI | у аккаунта OpenAI не пройдена Organization Verification — отдельный шаг помимо оплаты |
| `git push` ругается на файл больше 100 МБ | `node_modules` или `.venv` попали в git до появления `.gitignore` — нужно почистить историю |
